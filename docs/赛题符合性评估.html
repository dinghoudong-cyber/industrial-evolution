P0 · 阻断项：不补就没成绩

建议 5–7 天内全部关闭
P0-1

驱动模型被锁死在 DeepSeek，无法切到 PyTRiO / Qwen

红线
证据
config.py:77-80 三个字段全是字面量：provider: Literal["deepseek"]、base_url: Literal["https://api.deepseek.com"]、api_key_env: Literal["DEEPSEEK_API_KEY"]。写别的值 pydantic 直接校验失败。
影响
评测断网，api.deepseek.com 必然超时；每窗口白等 timeout 20s 后降级为规则策略。交付物里"大模型驱动 Harness"实际是空的，主观分「方法设计」与加分项「自主决策」直接归零。
改法
provider 改 openai_compatible，base_url/api_key_env/model 放开为普通字符串（默认 key 用 EMPTY，vLLM 接受任意值）；新增 configs/pytrio.yaml 指向 http://127.0.0.1:8000/v1 + Qwen3.8-27B；类名改 OpenAICompatProvider（保留 DeepSeek 别名）；smoke test 改成本地探活，配置里出现 api.deepseek.com 时启动即报错。
验收：断网机器上 llm-smoke-test 返回真实 Qwen 响应，且 llm_calls > 0、llm_fallbacks = 0 出现在 summary 里。
P0-2

镜像里根本没有 openai / swanlab 依赖

红线
证据
requirements.lock 只有 16 个包，openai、swanlab 都不在里面（它们是 pyproject.toml 里的 optional-dependencies）；Dockerfile 只 pip install -r requirements.lock。
影响
镜像里一旦开启 LLM，import openai 直接失败 → 永远走规则回退；SwanLab 同样 ImportError 被静默降级。也就是判分用的那个镜像，Harness 的大模型部分和记录能力都是死的。
改法
镜像内装 pip install -e ".[swanlab]" + httpx（或干脆不用 openai SDK，直接 requests 打 /chat/completions，少一个依赖、少一个版本风险）；把 openai/swanlab/httpx 固化进 lock 文件；加一个 --mode eval 启动自检：依赖缺失直接非零退出，而不是静默降级。
验收：容器内 python -c "import swanlab" 通过；--mode eval 启动打印依赖自检表。
P0-3

官方数据包没有适配层，现在只能跑合成流和自己格式的 CSV

红线
证据
只有 data/synthetic.py 与 data/stream.py；config.py:14-29 的 StreamConfig 字段全是合成参数（n_features、gradual_drift_start…），无法表达官方包的 train / valid / 评测脚本 / 隐藏流结构。README 第 164 行也把它列为"后续接入点"。
影响
数据包一发布，配置层就跑不起来；改造成本会落在最后一周，那是最危险的时间点。
改法
写 data/official.py：OfficialPackageStream 读 manifest（数据版本、特征清单、时间列、评测脚本入口），initial_data() 用 train+valid，__iter__ 按隐藏流顺序产窗；StreamConfig 改成 source: synthetic | csv | official 的判别式配置。先用自己造的假包（同目录结构、同命名）跑通，等真包落地只换路径。
验收：--source official --package <dir> 用假包跑完整 run，产物与合成流一致。
P0-4

镜像从未构建验证，且跑的不是评测入口

已闭环
原状
CMD 直接跑 cli demo --config default.yaml；没有 ENTRYPOINT、没有 run.sh、没有输出目录约定；configs/*.yaml 里 run_root 写死 D:/…，容器内会生成怪目录；镜像从未 build 过。
处理
run.sh 统一入口（demo / csv / smoke / check）；ENTRYPOINT ["/app/run.sh"] + ENV IE_CONFIG / IE_RUN_ROOT；run_root 改为相对 runs；补 ARG PIP_INDEX_URL 供国内构建换源（不影响锁定版本）。
实测
Docker Desktop 4.98 / 引擎 29.9.2 linux/amd64。构建 35 秒产出 546 MB 镜像；docker run --network none --memory 1g --cpus 1 --read-only 跑满 18 窗口、0 失败、耗时 7 秒；final_score 0.69906、v004 上线、holdout 0.660055，与宿主机逐位一致；docker save 产出 540 MB 离线包。
同时发现
镜像原先默认 default.yaml，其 max_historical_drop=0.06 会让 4 个候选全部被拒，整轮零更新，final_score 掉到 0.538。已把镜像默认配置改为 tuned.yaml（6 次尝试 / 4 次上线 / 0.69906）。
验收：docker run --network none -m 1g --cpus 1 image 一次跑完，退出码 0，摘要 run_status=complete。

P1 · 分数天花板：决定你能到 70 分还是 85 分

对应主观 65 + 加分 10
P1-1

SwanLab 记录太浅，撑不起《实验记录规范》

高
证据
tracking/swanlab_tracker.py:19-26：事件被塞成 {"event/type":…, "event/payload": str(payload)}，指标只留数值；没有 step、没有 log_artifact、没有 run 名称/标签/备注，swanlab.init 也没设 mode。
影响
评委打开链接看到的是一堆挤在一起的标量，看不到"这次改动的假设是什么、成本多少、结论是什么"。门槛②站不稳，65 分里的「实验规范与分析深度」也拿不到高分。
改法
一次实验一个 run（或一段带 step=window 的区间），run 名用 w12-retrain-h3 这种可读格式；config 里写死数据版本、触发原因、假设 ID、预期效果；log_artifact 上传 registry.json、决策日志、模型文件；summary 写 swanlab.log({"conclusion":...})；提供 mode=local/cloud/offline 三档。
验收：SwanLab 项目里有 ≥10 个带名称的 run，每个都能点开看到假设→配置→曲线→结论四段。
P1-2

「读历史→提假设→做实验→做决策」只做了最后一环

高
证据
llm/provider.py:10-30 请求体只有当前窗口的 15 个标量，无历史；policy/hybrid_policy.py:31-33 规则不更新就直接返回，LLM 仅对 RETRAIN_WITH_REPLAY 做二选一否决；llm/schemas.py:6-9 白名单只有两个动作。
影响
门槛③「至少 3 次」实际是 0 次。这不是补文档能解决的，是协议本身不支持。
改法
新增 experiment_memory.py：读历史 summary.json+metrics.csv，生成 history_digest（最近 K 次：假设 / 动作 / Δ主指标 / 成本 / 采纳与否）注入 prompt；动作白名单扩到 {no_update, retrain_with_replay, recalibrate_threshold, incremental_finetune, request_labels}；要求模型输出 hypothesis、expected_effect、cost_budget 三个字段；落库 decisions.jsonl（含决策前后指标），这就是可审计的决策链。
验收：decisions.jsonl 里能找到 ≥3 条带 hypothesis + 实验结果 + 采纳理由的完整链路，报告直接引用。
P1-3

第二层 RSI（策略自改进）整体缺位

高
证据
触发阈值、冷却期、回滚幅度全部写死在 configs/*.yaml；policy/rule_policy.py 只维护 signal_streak 与 last_update_window，没有任何参数自适应。
影响
赛题明写"模型层自迭代 + 策略层自改进"两层。只做一层，技术路线论证就是半篇；加分项里「长期表现 / 自主决策 / 成本收益」三项都依赖它。
改法
加 strategy_state.json（阈值、冷却、候选优先级、最小收益门槛）；每 N 个窗口做一次"策略更新提案 → 用历史窗口回测 → 采纳/拒绝"，并把这次更新本身也记成一个实验（元实验）。这是最容易拿 +10 的地方，也最能讲清"越做越聪明"。
验收：报告里有一张"策略参数随窗口演化"的曲线，且能说明第 X 窗口起无效更新占比下降。
P1-4

官方静态基线与成本公式没接，35 分没有优化目标

高
证据
configs/static.yaml 只是"自己关掉更新"的对照；budget.py 记的是秒/条/Token 绝对值，没有"单位增益消耗"这个量。主指标 balanced_accuracy 也写死在 adapter 里。
影响
门槛④无法自证；35 分客观分没有优化方向，报告里画不出"成本-增益"帕累托图——而那正是加分项「成本收益」要的东西。
改法
新增 cost.py：delta_metric_per_unit_cost = Δ主指标 / (GPU秒·系数 + 标注条数·系数 + Token·系数)，系数进配置；主指标名进配置；把官方静态基线分数与一次性评估结果落成 baseline.json，每次 run 自动对比并写进 summary。
验收：summary 里有 vs_official_baseline 字段；报告有帕累托散点。
P1-5

标注延迟与配额退场未建模，配额一耗尽整窗判失败

高
证据
orchestrator.py:270 每窗口直接 acquire_labels() 后立刻 score()；budget.py:26-31 超预算直接 raise BudgetExceededError，被 orchestrator.py:239 捕获后整窗记为失败，score 变 NaN。
影响
真实评测里标签大概率有延迟/分窗发放。配额一用完，性能曲线直接断掉，run_status 变 partial，甚至影响最终评分口径。
改法
labels.py 增加 label_lag_windows 与 label_budget_per_window；评估窗口与训练窗口解耦（用最近有标签窗口评估）；配额耗尽时降级为"只监测特征漂移、跳过评分"，而不是判整窗失败；把"要不要花配额要标签"变成策略动作之一。
