# 工业模型自进化系统：算力与Token需求说明

## 1. 结论

当前默认CPU配置的资源要求很低，DeepSeek开发接入为可选功能：

- 默认 `tuned.yaml`、`default.yaml` 和 `static.yaml` 不调用大模型；
- 默认实测Token为0；
- `deepseek-dev.yaml` 才会启用受控DeepSeek策略；
- 不使用GPU；
- 18窗口完整流程墙钟时间约1.13秒；
- 修复前测得Python进程峰值工作集约159.8 MiB；本轮未重新测量完整进程工作集；
- 7次模型训练累计约0.67秒；
- 五个正式模型文件合计约920.4 KiB。

这些数据描述的是当前CPU表格模型和默认离线配置。DeepSeek开发配置的Token由实际API响应单独计量；正式 Harness 使用 Qwen3.8 27B 或 4B，如选择基于 Qwen 的 PyTRiO 后训练，资源与Token仍需按赛题规则重新测量。

## 2. 实测环境

- 处理器：Intel Core i7-14650HX；
- 核心：16核；
- 逻辑处理器：24线程；
- Python：3.13；
- 模型：scikit-learn HistGradientBoostingClassifier；
- 数据：600条初始样本＋18个窗口×200条；
- 特征：8个数值特征；
- 配置：`configs/tuned.yaml`；
- GPU：未使用。

不同电脑的绝对耗时会不同，模型指标、动作顺序和样本数量不应改变。

## 4. 训练样本和标签

一次标准运行：

- 初始模型训练：480条；
- 初始验证/守护：120条，不进入训练回放；
- 每个候选训练：215条；
- 候选数量：6；
- 候选训练样本暴露量：1290条；
- 加上初始模型：共1770条训练样本暴露量；
- 首次访问并计入标签账本：4200条。

每个候选的215条由以下部分组成：

- 当前窗口训练部分：140条；
- 历史回放样本：75条。

标签账本不再只统计训练子集。它按稳定样本ID统计首次被评分、验证或训练访问的标签：

```text
初始600 + 18个窗口×200 = 4200条
```

同一标签用于评分、训练和守护时只计一次；训练回放中的历史标签也不会重复计费。正式比赛如何计算标签配额，仍须以组委会规则为准。

## 5. 每次候选训练时间

本轮标准运行6次候选训练加初始训练累计`0.670849秒`，完整流程墙钟时间`1.131061秒`。单次训练时间会随系统负载变化，因此预算以每次实际耗时逐项记录。

## 8. 默认配置为何是0 Token

默认系统使用确定性规则策略：

```text
漂移报告＋预算＋冷却期 → RuleBasedPolicy → 预定义动作
```

`tuned.yaml`、`default.yaml` 和 `static.yaml` 都没有启用大模型，因此：

- 输入Token：0；
- 输出Token：0；
- 大模型推理次数：0；
- 大模型微调次数：0。

这也是默认框架运行快、容易复现且可完全离线的原因。

### 8.1 DeepSeek离线集成实测

DeepSeek接入已经通过假提供商完成18窗口端到端测试。假提供商不访问网络、不产生费用，但会模拟API返回的usage，以验证账本和日志链路：

| 项目 | 结果 |
|---|---:|
| 进入LLM分支 | 6次 |
| 成功模拟响应 | 6次 |
| 模拟单次Token | 120 |
| 模拟累计Token | 720 |
| 训练尝试 | 6次 |
| 成功上线 | 4次 |
| 平均平衡准确率 | 0.676200 |
| 失败 | 0 |

`metrics.csv`中6行LLM决策的 `llm_total_tokens` 合计为720，`summary.json`的 `budget.tokens_used` 同样为720。这证明Token可以从响应一路进入窗口指标和总预算，但720不是DeepSeek真实计费数据。

这证明密钥缺失不会发出网络请求，也不会阻断模型闭环。系统继续采用规则建议，指标与离线调优配置一致。

### 8.3 DeepSeek真实连通实测

在用户明确授权后，使用固定模拟指标执行了一次成功的 `llm-smoke-test`：

| 项目 | 实测结果 |
|---|---:|
| 模型 | `deepseek-flash` |
| 动作 | `retrain_with_replay` |
| 置信度 | 0.85 |
| 输入Token | 295 |
| 输出Token | 148 |
| 其中推理Token | 110 |
| 总Token | 443 |
| API延迟 | 1.314259秒 |

测试只发送结构化模拟指标，不发送工业数据、文件、日志或密钥。Smoke Test结果直接显示在终端；它不创建运行目录。

此前第一次请求返回了未通过严格校验的内容。旧代码没有保留失败响应usage，因此该次用量需以DeepSeek控制台账单为准，不能把443视为两次请求的合计。当时在27项离线测试通过后，第二次请求成功；当前版本已扩展为35项测试。

执行完整 `demo --config configs\deepseek-dev.yaml` 时，可在对应运行目录查看：

- `summary.json`：`llm_attempts`、`llm_calls`、`llm_fallbacks` 和累计 `budget.tokens_used`；
- `metrics.csv`：每次调用的输入、输出、推理、总Token和延迟；
- `events.jsonl`：受控动作、置信度、模型名和回退原因。

日志不会保存API密钥、Authorization请求头或完整系统提示。

## 9. 真实接入大模型后的Token估算

下面是假设值，用于估算真实API或正式比赛模型的量级；它不同于第8节的离线模拟usage，也不是组委会公布的额度。

假设一次策略调用包含：

- 输入500 Token；
- 输出100 Token；
- 合计600 Token。

| 调用策略 | 调用次数 | 估算Token |
|---|---:|---:|
| 只在6次更新机会调用 | 6 | 3600 |
| 18个窗口每窗口调用 | 18 | 10800 |
| 每窗口进行3轮反思 | 54 | 32400 |
| 120窗口只调用6次 | 6 | 3600 |
| 120窗口每窗口调用 | 120 | 72000 |
| 120窗口每窗口3轮反思 | 360 | 216000 |

计算公式：

```text
总Token = 调用次数 ×（单次输入Token＋单次输出Token）
```

如果单次提示增加到1200 Token，表中数字需要乘2。

## 10. 推荐的低Token策略

建议正式Harness采用：

1. 规则系统先做漂移筛选；
2. 没有可执行漂移时不调用大模型；
3. 冷却期和预算不足时不调用大模型；
4. 只把结构化摘要传给大模型，不发送完整历史日志；
5. 大模型只能输出一个白名单动作和少量参数；
6. 每个决策最多调用一次；
7. 输出使用短JSON，限制最大Token；
8. 大模型失败时回退到当前规则策略。

建议第一版策略调用控制在：

```text
单次输入：300～600 Token
单次输出：50～120 Token
18窗口总量：优先控制在5000 Token以内
```

这只是工程目标，正式上限需要根据官方Token计分公式调整。

## 11. 27B模型是否需要本地GPU

赛题说明企业赛阶段由PyTRiO提供大模型训推额度，因此不应默认在本地电脑部署27B模型。

如果自行部署27B模型，仅模型权重的理论量级约为：

- FP16/BF16：约54 GB；
- INT8：约27 GB；
- 4-bit：约13.5 GB。

实际运行还需要KV缓存、框架和中间张量，因此显存或内存需求会更高。当前项目不承担这部分本地算力，应该通过官方PyTRiO服务调用。

## 12. 正式比赛中的不确定项

目前PDF没有给出：

- 隐藏测试流窗口数量；
- GPU时长具体上限；
- Token具体上限；
- 标注配额具体数值；
- 三类成本的权重；
- PyTRiO调用单次上下文限制；
- 大模型微调如何计费。

因此当前可以证明系统资源很轻，但不能承诺正式比赛的最终资源分数。

## 13. 建议结论

当前CPU框架和默认离线配置的算力与Token要求都不高：

- 普通CPU即可运行；
- 无需GPU；
- 约160 MiB峰值进程内存；
- 18窗口约1.14秒；
- 模型文件不到1 MiB；
- 默认配置Token为0。

DeepSeek开发链路已经验证Token记账和故障回退：假提供商模拟6次调用共720 Token；缺少密钥时为6次尝试、0次成功API调用、0 Token，并由规则策略完整接管；一次成功的真实连通测试使用443 Token、延迟约1.31秒。首次未通过JSON校验的请求可能另有计费，应以DeepSeek控制台为准。未来正式接入大模型时，主要风险不是基础模型训练，而是调用频率和上下文长度。使用“规则筛选＋事件触发＋短JSON输出”的方案，可以把Token控制在较低水平。
