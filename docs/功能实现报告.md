# 第 1 章 系统是什么

## 1.1 一句话版本

**给工业模型装了一个"自动驾驶"**：它自己盯着数据有没有变、判断为什么变、决定要不要重训、训完先考试再决定上不上线，上线后继续盯，一旦发现退步就自动退回上一版。

人工做这件事的流程是：数据工程师看监控 → 算法工程师判断 → 训练 → 评估 → 上线 → 出问题回滚。这个系统把这条链路做成了一条自动流水线，**中间不需要人点确认**，而且每一步都留下可复核的证据。

## 1.2 它解决的痛点

工业场景里的模型不是"训一次用三年"。设备老化、原料批次更换、季节变化、工艺调整，都会让输入数据的分布慢慢偏移（叫**数据漂移**）。模型本身没坏，但它见过的世界变了，判断就开始失准。

传统做法有两个坑：

- **只监控不动作**：看板上画着准确率在掉，但要等到人发现、排期、重训，往往已经过了几周。
- **一有风吹草动就重训**：算力、标注、Token 都是钱，而且新模型不一定比旧的好——没有把关的自动更新，本质是把风险自动化了。

这套系统的定位在中间：**该动的时候果断动，动之前必须有证据，动完必须能退回来。**

## 1.3 输入什么、输出什么

| | 内容 | 形式 |
|---|---|---|
| **输入 1** | 一批带标签的历史数据（冷启动用） | CSV 或内置合成数据 |
| **输入 2** | 按真实时间顺序到达的数据流，切成固定大小的窗口 | CSV / 官方数据包 / 合成流 |
| **输入 3** | 一份配置（阈值、预算、策略开关） | YAML |
| **输出 1** | 每个窗口的判断：漂不漂、什么漂、做了什么、结果如何 | `metrics.csv` + `events.jsonl` |
| **输出 2** | 模型版本链（v000、v001……），每个版本可加载、可回滚 | `models/` |
| **输出 3** | 整轮运行的结论摘要 | `summary.json` |
| **输出 4**（可选） | 云端实验看板，含曲线、判断链、可复算产物 | SwanLab |

## 1.4 它一共只会做四件事

这里要强调：**动作空间很小，是故意的。**

```
        ┌──────────────────────────────────────────────┐
        │  每个窗口只允许四种动作                       │
        ├──────────────────────────────────────────────┤
        │  no_update              什么都不做，继续观察   │
        │  retrain_with_replay    带历史回放重训候选     │
        │  rollback               退回上一版（连记忆一起）│
        │  error                  本窗处理失败，兜底继续 │
        └──────────────────────────────────────────────┘
```

动作少，是因为工业系统里"能做的事越多，越容易做出没法解释的事"。策略大模型（LLM）就算接进来，也只能在这四个动作里选，而且只能选前两个——**它没有权限绕开预算、冷却、评估和回滚**。这条边界写在 JSON 结构校验里，不是靠提示词求它别乱来。

## 1.5 闭环的六步

```text
  ┌─────────┐   ┌─────────┐   ┌────────┐   ┌───────┐   ┌──────────┐   ┌──────────────┐
  │ monitor │──▶│diagnose │──▶│ decide │──▶│ train │──▶│ evaluate │──▶│ deploy/reject│
  └─────────┘   └─────────┘   └────────┘   └───────┘   └──────────┘   └──────┬───────┘
       ▲                                                                       │
       │                         ┌──────────┐                                  │
       └─────────────────────────│ rollback │◀─────────────────────────────────┘
                                  └──────────┘        上线后继续观察
```

这六步在代码里对应 11 个状态（`RunState`），每次状态跳转都会往事件流里写一条 `state_transition`。**所以"闭环有没有真的跑完"不用信口头描述，数事件就能验证。**

## 1.6 和赛题要求逐条对上

| 赛题要求 | 系统里的实现 | 代码位置 | 怎么验证 |
|---|---|---|---|
| 五步闭环、无人干预 | `EvolutionOrchestrator.run()` 一个循环跑完，不读 stdin、不等人 | `orchestrator.py` | `demo` 跑完退出码 0，事件流里 18 个窗口全有记录 |
| 驱动模型只能用允许的模型 | provider 层锁死：`deepseek` 只允许官方域名，评测走本地 OpenAI 兼容端点 | `llm/`、`config.py` 校验 | `llm` 配置写错直接启动失败 |
| 全程留痕 | 本地三层（事件/指标/摘要）+ SwanLab 三层（曲线/判断链/产物） | `tracking/` | 标准 18 窗运行产出 140 条事件、18 行 × 31 列指标 |
| 不能只针对公开集调优 | 训练/评估/守护集三重隔离，配置里没有"针对测试集"的开关 | `training/`、`evaluation/` | 测试用例 `test_tuned_profile_preserves_deterministic_leak_free_behavior` |
| 综合性能不低于静态基线 | 同一份数据、同一个种子，静态 vs 自进化有对照 | `configs/static.yaml` | 第 8 章的对照表 |
| 成本可核算 | 预算账本按"首次访问计费"，四类资源独立记账 | `budget.py` | `summary.json` 的 `budget` 字段 |

# 第 2 章 一次运行发生了什么

这一章按时间顺序讲。每一步都说清三件事：**做什么、怎么做的、失败会怎样**。

## 2.0 全局图

```text
启动
 ├─ 读 YAML，严格校验（多写一个字段都会报错）
 ├─ 建 runs/run-时间戳-随机码/ 目录
 ├─ 取初始数据 → 8:2 切成"训练集 / 验证集"
 ├─ 训练 v000（第一个冠军模型）
 ├─ 用训练集建"参考分布"（后面判断漂移的尺子）
 ├─ 从验证集切出"守护集"（永不参与训练的考试真题）
 └─ 进入窗口循环
      │
      ├─ 窗口 0：计费标签 → 特征漂移 → 打分 → 性能漂移 → 诊断 → 决策 → (训练?) → 记录
      ├─ 窗口 1：同上
      ├─ ……
      └─ 窗口 17：同上
      │
收尾
 ├─ 算三种分数（最后窗口分 / 最终部署模型分 / 平均分）
 ├─ 写 summary.json
 └─ 关记录器（本地先写，云端后传）
```

## 2.1 启动阶段

**① 读配置，宁可启动失败也不带病运行**

`config.py` 用 Pydantic 的 `extra="forbid"`，意思是 YAML 里多写一个不存在的字段就直接报错。这听起来很烦，但工业配置最怕的就是"以为改了其实没生效"——写错名字被静默忽略，跑出来结果不对，排查要花几天。

除了字段名，还有跨字段的约束：

- `gradual_drift_start` 必须小于 `abrupt_drift_start`，否则合成数据的两个漂移阶段会重叠；
- LLM 的公网端点必须 https，本机/内网才允许 http；
- `api_key_env` 必须是大写、且以 `API_KEY` 或 `TOKEN` 结尾——防止有人把配置改成读 `PATH` 之类的变量往外发。

**② 分初始数据：8 : 2**

```python
split = min(len(y) - 1, max(1, int(len(y) * 0.8)))
```

前 80% 训练 v000，后 20% 做验证。为什么留 20%？因为如果拿训练集自己的分数当基线，模型会显得比实际好，后面的"性能下降"就永远触发不了。

**③ 从验证集里再切一块"守护集"**

```python
guard_count = min(config.validation.guard_samples, len(y_valid))
```

守护集是**整个系统里最重要的一个设计**。它有三条铁律：

1. 永远不参与任何训练（训练时会显式排除它的样本 ID）；
2. 每次候选上线都要在它上面考一次；
3. 整轮运行期间**固定不变**——它不随窗口更新，也不因部署而改变，这正是它能当稳定标尺的原因。

打个比方：守护集就是"高考真题"。平时练习（训练）可以用任何资料，但真题必须留到考场上用，而且每次换教材后都要用同一套真题重新考一遍，才能比较。

**④ 训练 v000 并注册**

`ModelRegistry.register()` 把模型存成 `v000.joblib`，同时在 `registry.json` 里追加一条记录，写上来源、分数、训练耗时。写文件的方式是**先写 `.tmp` 再 `os.replace`**——这是原子替换，进程中途被杀也不会留下半个坏文件。

**⑤ 建"参考分布"**

`FeatureDriftDetector` 拿训练集算每个特征的统计量：分位数边界、直方图占比、标准差。这些量只算一次并缓存，后面每个窗口只需要拿新数据往这套"尺子"上量，不用反复扫历史数据。

## 2.2 每个窗口的十个步骤

### 第 1 步：计费标签

```python
self.budget.acquire_labels(window.sample_ids)
```

**为什么第一件事是记账？** 因为标签是要花钱的（人工标注、或者等真实结果回传）。如果先算分再记账，一旦超预算抛异常，分已经算出来了——等于白嫖了一次标注。

账本内部用 `set` 存已计费过的样本 ID，同一批数据重复进来只算一次钱。这个细节很关键：`README` 里那个"4200 个不同标签"就是去重后的结果，不是窗口大小乘以窗口数（200 × 18 = 3600 加上初始 600 正好 4200，数字对得上，说明没有重复计费）。

### 第 2 步：特征漂移

对每个特征算四个量，再归一化成一个"严重度"：

| 指标 | 它回答什么 | 用大白话解释 |
|---|---|---|
| PSI | 分布形状变了多少 | 把数据切成 10 个桶，比较每个桶里的人占比变化 |
| KS | 累积分布最大差多少 | 两条曲线之间最远的那段距离 |
| Wasserstein | 整体平移了多远 | 把一堆土搬成另一堆形状要费多少力，再除以标准差 |
| 缺失率变化 | 数据质量有没有变差 | 空值/无穷值比例涨了多少 |

四个量单位不同，不能直接比。做法是**各自除以自己的阈值**，变成"超标几倍"，然后取最大值：

```python
severity = max(psi / psi_threshold, ks / ks_threshold,
               wasserstein / 0.35, missing_delta / non_finite_threshold)
```

这样 1.0 就是"刚好到线"，2.0 就是"超一倍"，跨特征可比。

整体判定有两条路，满足任一条就算漂移：

- **多数特征报警**：漂了的特征数 ≥ 总特征数的 20%（至少 1 个）；
- **少数特征特别严重**：严重度最高的 3 个特征平均值 ≥ 1.25。

为什么要有第二条？因为工业里经常是"8 个传感器里 1 个坏了"，按比例算永远不够 20%，但那一个特征的偏移已经足以毁掉预测。

**数据质量不合格直接熔断。** 如果某个特征有效值少于 5 个，抛 `DataQualityError`，这个窗口标成 `data_quality_failed`，不进后续流程。这是防止"用垃圾数据算出一个看起来很正常的分数"。

### 第 3 步：给当前冠军打分

```python
score = runtime.champion.score(window.X, window.y)
```

分类任务用**平衡准确率**（每个类别各算召回率再平均），不用普通准确率。因为工业缺陷检测里正样本可能只占 3%，全猜"正常"也能有 97% 准确率，这个数字毫无意义。

分数必须是有限值，否则同样熔断。

### 第 4 步：性能漂移

两个检测器同时工作：

- **滚动均值对比基线**：最近 3 个窗口的平均分，比部署时的基线低了多少；
- **Page-Hinkley**：一种累积和检验，专门抓"缓慢但持续"的下降。它累加"当前值 − 历史均值 − 容忍度"，一旦累积偏离超过阈值就报警。

为什么两个都要？滚动均值对突变敏感、对渐变迟钝；Page-Hinkley 相反。两个一起用，突变和缓降都能抓到。而且必须攒满 3 个窗口才允许报警——这是为了过滤单窗口的随机波动。

### 第 5 步：诊断，把"报警"翻译成"病因"

三个信号源：特征漂移、性能漂移、标签分布漂移（用总变差距离，简单说就是"两类样本的比例变化了多少"）。组合出五种结论：

| 特征漂移 | 性能下降 | 标签漂移 | 结论 | 含义 |
|---|---|---|---|---|
| 有 | 有 | 任意 | `mixed` 混合漂移 | 世界变了，模型也确实跟不上了 |
| 无 | 有 | 任意 | `concept_suspected` 概念漂移疑似 | 输入没变但"输入→输出"的规律变了 |
| 有 | 无 | 有 | `mixed` | 输入和类别比例同时变 |
| 有 | 无 | 无 | `covariate` 协变量漂移 | 只是输入分布变了，规律还没变 |
| 无 | 无 | 有 | `label` 标签漂移 | 只是各类样本比例变了 |
| 全无 | | | `none` | 不动 |

**这一步的输出不是给机器看的，是给人看的。** `explanation` 字段会写成"输入漂移，重点特征：sensor_00, sensor_01；滚动性能下降 0.0850"这样一句话，直接进事件流和 SwanLab 文本层。评审想知道"你为什么决定重训"，答案在这一句里。

### 第 6 步：决策（这里有两道关）

**第一道：要不要回滚？** 注意回滚判断在决策之前，因为"模型坏了"比"要不要再训一个"更紧急。

```python
threshold = last_deployment_score - rollback_drop
if score < threshold: streak += 1
else: streak = 0
```

连续 `rollback_patience`（默认 2）个窗口都低于"部署分 − 容忍度"，才真的回滚。单个窗口失手不算，避免被一次数据抖动带着来回横跳。

**第二道：规则策略。** 四道闸门依次过：

```text
有没有可执行的漂移？ ──没有──▶ no_update
        │有
连续确认够不够？ ──不够──▶ no_update（等下一个窗口）
        │够
冷却期过了吗？ ──没过──▶ no_update（刚更新完，别连环炸）
        │过了
预算还够吗？ ──不够──▶ no_update（记 budget_exhausted）
        │够
        ▼
retrain_with_replay
```

这四道闸门是**硬编码的**，LLM 改不了。LLM 只能在这个结果已经是"要训练"的前提下，说"我同意"或"我建议再等等"。

标签预算还有一道更早的**窗口准入检查**：每个窗口先用样本 ID 去重计算需要揭示的新标签数。若超出 `max_labels`，窗口记为 `budget_skipped` / `no_update` 并写入 `window_skipped`，不评分、不诊断、不调用策略、不进入回放，也不部分扣费。它不计入 `successful_windows` 或 `failures`，而单独计入 `skipped_windows`；有成功窗口且发生跳过时整次运行标为 `partial`，全窗口跳过仍为 `failed`。实际 API Token 或训练耗时在执行后才确认超限时，继续走预算熔断和失败留痕，不伪装成普通跳过。

### 第 7 步：训练候选

**切分**：本窗口的数据按 `holdout_fraction`（默认 0.30）切开——前 70% 拿去训练，后 30% 留着考试。

**采样**：训练集 = 本窗前 70% + 历史回放。回放条数按比例算：

```python
replay_count = len(recent) * (1 - recent_fraction) / recent_fraction
```

`recent_fraction = 0.65` 意味着"新数据占 65%，历史占 35%"。这个比例是个平衡点：新数据太少学不到新规律，太多会把旧知识忘光（灾难性遗忘）。

回放采样时会**排除守护集 ID**，采完还要再检查一遍有没有重叠，发现重叠直接抛异常。这是防止"复习的时候不小心把高考真题当练习题做了"。

**训练**：候选模型是**从零训练**的（`champion.new_unfitted()`），不是在旧模型上继续拟合。工业表格数据用 HistGradientBoosting，140 轮、学习率 0.08、叶子 15 个，这个规模在 CPU 上单次训练 1~2 秒，符合"限时"要求（实测 5 个候选版本分别耗时 1.23~1.31 秒）。

### 第 8 步：双考

候选要同时通过两场考试：

| 考试 | 考题 | 及格线 | 防的是什么 |
|---|---|---|---|
| 本窗 holdout | 本窗口后 30%（没参与训练） | 比冠军高 ≥ `min_improvement`（0.008） | 防止"训了个更差的" |
| 历史守护集 | 从初始验证集切出来的固定样本 | 比冠军低 ≤ `max_historical_drop`（0.10） | 防止"学了新的忘了旧的" |

两个都过才上线。只过第一个，说明模型在追新数据时把老本事丢了；只过第二个，说明它根本没学到新东西。

### 第 9 步：上线或拒绝

**上线**要做五件事，顺序不能乱：

1. 换内存里的冠军模型；
2. 注册新版本 `vNNN`（落盘 + 更新注册表）；
3. **更新特征参考分布**（尺子跟着新模型一起换，否则下一个窗口会拿旧尺子量新世界，永远报漂移）；
4. 更新标签参考分布、重置性能基线；
5. **把当前所有监测状态打包成快照**，存进 `deployment_states[version]`。

第 5 步是回滚能成功的关键，下一章细讲。

**拒绝**就很简单：切到 `REJECT` 状态，`updates_rejected += 1`，模型不动，等下一个窗口。

### 第 10 步：写证据

每个窗口结束后写三样东西：

- `metrics.csv` 一行：分数、漂移量、动作、状态、四类预算消耗、LLM 用量；
- `events.jsonl` 若干条：状态跳转、诊断详情、决策理由、候选评估结果；
- 一条**假设链**：观察 → 诊断 → 决策 → 预期 → 结果 → 判定。

假设链是这套系统区别于"普通 AutoML 脚本"的地方。它把每个窗口当成一次**可被反驳的科学假设**。决策段同时保留窗口最终动作 `action` 和策略给出的 `proposed_action`：正常时两者一致；若策略返回后发生实际 Token 超预算，最终动作会是 `error`，但策略建议、已知 Token 用量、调用信息仍写入该窗口记录。此时 `outcome.status` 是 `budget_exhausted`，判定为 `inconclusive`，不能把建议动作误当作已经执行的更新。`fallback_reason`、`policy_reason` 和 token usage 都按当时可得信息记录；缺失值不推断。

下面这两条是 `runs/report-check` 那次运行里**真实写下的记录**（原文照录，只删了缩进）：

## 2.3 收尾：三个分数，别搞混

这是最容易误读的地方，单独讲。

| 字段 | 含义 | 什么时候有值 |
|---|---|---|
| `final_score` | **最后一个窗口**给当时冠军打的分 | 只要有窗口成功就有 |
| `final_deployed_score` | **最终上线的那个模型**在上线时 holdout 上的分 | 只有该版本是"评估通过上线"的才有 |
| `final_deployed_guard_score` | 同一时刻在历史守护集上的分 | 同上 |
| `final_mean_score`（`mean_score`） | 所有窗口分数的平均 | 有窗口就有 |

为什么不能只报一个数？因为**部署发生在打分之后**。窗口 17 打完分（此时冠军是 v003，得 0.699060），然后才决定把 v004 上线。v004 再也没被任何窗口评过分——如果直接拿 0.699060 当"最终模型成绩"，那是拿前任的成绩给现任贴金。

所以系统额外记录 `final_deployed_score = 0.660055`（v004 上线时在 holdout 上的真实得分），并写明来源 `candidate_holdout_window_17`。这个数字**比 0.699 低**，说明最后一次上线在这一窗并没有带来提升——结论如实写在摘要里，不做修饰。

如果最终模型不是评估上线的（比如跑的是静态配置，一次都没更新），这两个字段给 `null`，并写一条 `final_deployment_score_missing` 事件说明原因。**绝不拿旧分数顶替。**

# 第 3 章 六个关键机制，怎么实现的

## 3.1 三重锁：怎么保证不偷看答案

数据泄漏是这类比赛最常见的失分点，也是最难自证清白的地方。系统用三把独立的锁：

**第一把锁：时间顺序不可打乱。**
CSV 流按原始行顺序切窗（`iloc` 切片），全程没有 `shuffle`、没有 `sort_values`。窗口 i 只看得到窗口 i 及之前的数据。

**第二把锁：训练/考试分离。**
每窗数据按 70/30 切，候选只用前 70% 训练，后 30% 考试。守护集单独存在，任何训练都显式排除它的 ID：

```python
replay.sample_with_ids(n, exclude_ids=guard_id_set)
...
if set(outcome.training_sample_ids.tolist()) & guard_id_set:
    raise RuntimeError("候选训练数据与历史守护集重叠")
```

注意这里是**双重检查**：采样时排除一次，训练完再断言一次。多写一行代码，换的是"永远不会悄悄泄漏"。

**第三把锁：ID 全局唯一。**
官方数据包接入时会检查初始集和评测流的样本 ID 有没有交集：

```python
_assert_ids_disjoint()   # 发现重复直接报错，并打印重复的 ID 示例
```

如果两边用了同一批样本，守护集就会和训练集重叠，评估结果虚高。这个问题在真实数据包里非常常见（尤其是初始集是从流里"捞"出来的），所以在启动阶段就拦掉。

## 3.2 预算账本：钱是怎么算的

四个独立账户，各自有上限：

| 账户 | 记什么 | 什么时候扣 |
|---|---|---|
| 更新次数 | 训练了几次候选 | 训练开始时（失败也扣） |
| 训练时间 | 累计训练秒数 | 训练结束后按实际耗时 |
| 标注量 | 见过多少个**不同**样本的标签 | 每个窗口开始、初始训练开始 |
| Token | LLM 调用消耗 | 每次调用后按返回的 usage |

三个设计细节值得说：

1. **失败也计费**。`record_update` 在 `try/except` 的两条路径上都调用——训练崩了也占用了算力，凭什么不算钱？
2. **超支即熔断**。`record_tokens` / `_record_training_seconds` 一旦发现累计超限，`budget_violations += 1` 然后抛 `BudgetExceededError`。这个窗口记成失败，但整轮运行继续。
3. **先问再花**。决策前用 `can_train()` 问一次"还够不够"，不够就返回 `no_update` 并说明原因，而不是花了钱再报错。

## 3.3 双考上线：为什么敢自动换模型

`ChampionChallengerEvaluator` 只有 60 行，但它是整个系统的"刹车"。

```python
if improvement < min_improvement:        # 新模型没变好
    accepted = False
elif historical_drop > max_historical_drop:   # 新模型把老本事丢了
    accepted = False
else:
    accepted = True
```

两个阈值的设计取向完全不同：

- `min_improvement = 0.008` 很小，意思是"只要真的有一点点进步就认"。为什么不设高？因为漂移期数据本身噪声大，门槛太高会导致永远不更新，系统退化成静态基线。
- `max_historical_drop = 0.10` 相对宽松，但它防的是灾难性遗忘。这个值不能设太严：`default.yaml` 里原来是 0.06，实测导致 4 个候选全被拒、整轮零更新，最后分数从 0.734 掉到 0.538。改成 0.10 之后才有 4 次成功上线。**这是一个用真实运行换来的参数，不是拍脑袋定的。**

## 3.4 回滚：不是换模型，是"连记忆一起退"

大多数"自动回滚"只做一件事：把模型文件换成上一版。这套系统多做了一步——**把监测状态一起回退**。

为什么？举个具体例子：

假设 v003 部署时，特征参考分布是"夏天"的数据。后来切到 v004，参考分布更新成"秋天"。现在 v004 表现不好要回滚到 v003。如果只换模型文件、不换参考分布，那 v003 会拿"秋天"的尺子去量"夏天"的模型，下一个窗口立刻报一个假漂移，然后又触发一轮莫名其妙的更新。

所以每个版本上线时都存一份完整快照：

```python
@dataclass
class _DeploymentSnapshot:
    feature_state: dict      # 特征参考数据（整张表）
    performance_state: dict  # 基线分、滚动窗口、Page-Hinkley 累积量
    diagnosis_state: dict    # 标签参考分布
    policy_state: dict       # 连续信号计数、上次更新窗口
    deployment_score: float  # 上线时的分数
```

回滚时按相反顺序恢复，并且**带回滚保护**：如果恢复过程中出异常，先把当前状态恢复回去，再抛错——不能出现"回滚到一半，系统处于既不是新版也不是旧版"的状态。

## 3.5 两层决策：规则兜底，LLM 只能否决

这是"安全可控"分项的核心设计。

```text
                    ┌──────────────┐
   窗口信号 ────────▶│ 规则策略      │
                    │ 4 道硬闸门    │
                    └──────┬───────┘
                           │
              ┌────────────┴────────────┐
              │ 结论是"不训练"           │ 结论是"要训练"
              ▼                         ▼
           直接返回              ┌──────────────┐
        （LLM 不会被调用）       │ LLM 复核      │
                                │ 只能同意/否决  │
                                └──────┬───────┘
                                       │
                     ┌─────────────────┼─────────────────┐
                     ▼                 ▼                 ▼
                  同意训练          否决              任何异常
                     │                 │                 │
                     ▼                 ▼                 ▼
              retrain_with_replay  no_update      回退规则结论
                                  （缓存 N 窗）
```

**七道闸门**保证 LLM 不会乱花钱：

1. 规则没说要训练 → 不调用（省 Token，也避免 LLM 在平稳期瞎折腾）；
2. 调用次数用完（`max_calls`）→ 回退；
3. 剩余 Token 不够一次调用 → 回退；
4. 最近刚否决过 → 直接复用结论，不重复调用（`call_cooldown_windows`）；
5. 返回置信度低于 `min_confidence` → 回退；
6. 端点异常/超时 → 回退，并把异常类型写进 `fallback_reason`；
7. 返回的 JSON 不符合白名单 → 回退。

第 7 条值得展开：LLM 的输出必须能通过 `LLMDecisionPayload` 校验——

```python
action: Literal["no_update", "retrain_with_replay"]
confidence: float = Field(ge=0.0, le=1.0)
reason: str = Field(min_length=1, max_length=240)
extra = "forbid"   # 多返回一个字段都算失败
```

也就是说，**它连"rollback"这个词都说不出来**，因为枚举里没有。这不是提示词约束，是代码约束。

## 3.6 留痕：三层记录，本地优先

```text
写入路径：
  业务代码 ──▶ CompositeTracker ──┬──▶ LocalTracker（主记录，必成功）
                                  └──▶ SwanLabTracker（镜像，可失败）

close 顺序：先写本地 summary.json ──▶ 再让镜像上传
```

镜像的容错是"连续失败 5 次才停用"，不是一次失败就踢掉。因为网络抖动很常见，一次就停用会让整轮记录残缺。

SwanLab 这层分三块：

| 层 | 内容 | 给谁看 |
|---|---|---|
| 曲线 | 每窗口分数、漂移量、预算，`step` = 窗口序号 | 看趋势、多轮对比 |
| 文本 | 关键事件 + 每条假设链（六段式） | 想知道"为什么这么决定" |
| 产物 | summary / metrics / events / 注册表 作为 run 文件 | 想复算的人 |

有个坑必须记下来：**SwanLab 0.10 收到字符串标量会抛 `TypeError` 并在内部吞掉**，列会静默变空。所以状态类字段统一转数值码（`action: retrain_with_replay → 1`），码表写在 `_CODEBOOK` 里，可读名字保留在文本层。这是实测踩出来的，不是看文档看来的。

## 4.1 根目录：入口与契约

### `README.md`

**职责**：给第一次接触项目的人一条最短路径——看懂能力、跑起来、知道去哪查细节。

**实现方法**：不是罗列功能，而是按"读者意图"组织：主要能力 → 策略模型接入 → 快速开始 → 用自己数据 → 官方数据包 → 配置表 → 容器 → 记录 → 产物 → 对照结果 → 项目结构 → 后续接入点。

**关键设计**：对照结果那一节写明了 `final_score` 和 `final_deployed_score` 的差别，并主动写出"最后一次上线没带来提升"这个负面结论。**文档里敢写坏消息，评审才会信好消息。**

### `pyproject.toml`

**职责**：定义包元数据、依赖、可选依赖、ruff 与 pytest 配置。

**实现方法**：`[project.optional-dependencies]` 里分出 `dev`（pytest/ruff）和 `swanlab`；`[tool.ruff]` 设行宽 100，`[tool.pytest.ini_options]` 设测试路径。这样 `pip install -e ".[dev]"` 一条命令就能装出开发环境。

### `requirements.lock`

**职责**：把核心依赖精确到版本号，保证"我这能跑，你那也能跑"。

**实现方法**：全部用 `==` 锁定，镜像构建时直接按这个文件装，不做版本求解——求解会引入"今天装和明天装不一样"的风险。

### `requirements-extras.txt`

**职责**：只装可选能力（`openai>=1.0`、`swanlab>=0.10.4,<1.0`）。

**实现方法**：单独一个文件、用区间约束而不是精确 pin。因为这些库更新快，锁死版本反而容易和 Python 3.13 冲突。Dockerfile 里分两层装，也是为了"核心依赖变了才重装，可选依赖单独缓存"。

### `Dockerfile`

**职责**：把整个系统打进一个能在断网、限内存环境里跑的镜像。

**实现方法**（每条都有原因）：

| 做法 | 原因 |
|---|---|
| 基础镜像 `python:3.13.7-slim-bookworm` | slim 版省 400MB，bookworm 比 alpine 的 wheel 兼容性好 |
| `ENV PYTHONUTF8=1` | 容器里 locale 常常是 POSIX，中文输出会乱码 |
| layering：先 COPY requirements 再 COPY src | 改代码不用重装依赖，构建从 15 分钟降到 35 秒 |
| `ARG PIP_INDEX_URL` 默认官方源 | 评测方按原样构建不需要额外参数；国内构建时传阿里云源 |
| `pip install --no-build-isolation --no-deps .` | 依赖已经装过了，不再求解一遍 |
| 建 `runner` 用户（uid 10001） | 不以 root 跑，符合最小权限 |
| `ENTRYPOINT ["/app/run.sh"]` + `CMD ["demo"]` | 运行契约固定：`docker run <image> <mode>` |
| `ENV IE_SWANLAB=1` + `IE_SWANLAB_MODE=offline` | 评测机无外网也默认留痕，落盘后可补传 |

### `run.sh`

**职责**：容器内唯一入口，把"评审想干什么"翻译成"内部 python 命令"。

**实现方法**：`case "$MODE"` 分派五种模式，环境变量拼成参数数组：

```bash
RECORD_ARGS=()
[ "$IE_SWANLAB" = "1" ] && RECORD_ARGS+=(--swanlab)
[ -n "$IE_SWANLAB_MODE" ] && RECORD_ARGS+=(--swanlab-mode "$IE_SWANLAB_MODE")
```

注意 `set -euo pipefail` 和 `: "${IE_CSV:?csv 模式需要设置 IE_CSV}"`——缺参数时报一句人话，而不是让 python 抛一串栈。

### `运行演示.bat`

**职责**：Windows 上双击就能跑，不用开终端。

**实现方法**：`chcp 65001` 切 UTF-8 防乱码，先检查 `.venv\Scripts\python.exe` 存在，再调 `demo --config configs\tuned.yaml`，最后按退出码打印成功/失败并 `pause` 让人看到结果。

### `.env.example`

**职责**：告诉使用者需要哪些密钥、放哪。

**实现方法**：三个变量都留空，附一句"不要把真实密钥写进 YAML、镜像或提交记录"。**模板文件里绝不能有真值**，否则复制粘贴一次就泄漏了。

### `.gitignore` / `.dockerignore`

**职责**：阻止不该进版本库/镜像的东西进去。

**实现方法**：两份规则，目标不同。

- `.gitignore` 管版本库：忽略 `.venv/`、`runs/*`（保留 `.gitkeep`）、`__pycache__/`、`.pytest_cache/`、`*.egg-info/`、`build/`、`dist/`、`.env` 和 `.env.*`（但放行 `.env.example`）。
- `.dockerignore` 管镜像体积：在前者基础上再排除 `tests/`、`docs/`、`*.joblib`、`docker-runs/`、`*.prof`、`.idea/`、`.vscode/`。

这个差别很关键：镜像里不需要测试和文档，也不需要 1.2GB 的 `.venv`——漏掉一条，镜像就会从 546MB 涨到几个 GB，构建和分发时间成倍增加。

## 4.2 `configs\`：六份配置，一套结构

**职责**：所有可调参数集中在这里，代码里不写死任何阈值。

**实现方法**：六份文件结构完全相同，只在数值和开关上有差异。这样切换配置就是换一个文件路径，不用改代码。

| 配置 | 用途 | 与 `tuned` 的差异 |
|---|---|---|
| `tuned.yaml` | **推荐演示配置**，当前默认 | — |
| `default.yaml` | 保守起点 | 连续确认 2 窗、冷却 2 窗、`max_historical_drop` 0.06（实测会导致零更新） |
| `static.yaml` | 静态对照组 | `max_updates: 0`，一次都不许更新 |
| `official.yaml` | 官方数据包起点 | 预算放宽（8 次/240 秒/2 万标签/8000 Token）、守护集 800 |
| `deepseek-dev.yaml` | 联网开发验证 | `llm.enabled: true`、`provider: deepseek` |
| `local-qwen.yaml` | 本地 Qwen 评测 | `provider: openai_compatible`、`http://127.0.0.1:8000/v1`、免鉴权 |

**为什么要有 `static.yaml`？** 因为"自进化比静态好"这句话必须能被证伪。同一份数据、同一个种子，跑一遍静态、跑一遍自进化，两条曲线摆在一起才有说服力。这个配置就是那个对照组的开关。

**改它的风险**：`validation.max_historical_drop` 和 `monitoring.consecutive_windows` 是最敏感的两个参数。前者太严会导致永不更新（实测过），后者太松会导致频繁误触发。改之前先看第 6 章的影响说明。

if provider == "deepseek" and host != "api.deepseek.com": 报错

### `orchestrator.py`：整条流水线的调度器（846 行，最核心）

**职责**：串起所有模块，管状态机、管窗口循环、管异常兜底、管记账。

**实现方法**：一个主循环 + 十几个私有方法。分解：

| 方法 | 干什么 | 关键点 |
|---|---|---|
| `run()` | 初始化 + 遍历窗口 + 收尾 | 循环体只有一句 `_process_window`，异常不外抛 |
| `_initialize_runtime()` | 分数据、训 v000、建尺子、切守护集 | 训练失败也记账 |
| `_process_window()` | 单窗口主流程 | `try/except` 包住整窗，失败落 `_handle_window_failure` |
| `_monitor_and_diagnose()` | 特征漂移 + 打分 + 性能漂移 + 诊断 | 数据质量不合格直接抛 |
| `_try_rollback()` | 回滚判断与执行 | 带"回滚失败再恢复"的保护 |
| `_decide_and_update()` | 策略决策 + LLM 记账 | 预算不足改写 `status` |
| `_train_and_evaluate()` | 训练 + 双考 | 训练完再断言一次无重叠 |
| `_deploy_candidate()` | 上线五件事 + 快照 | 顺序不能乱 |
| `_handle_window_failure()` | 兜底 | 分类标记 `data_quality_failed` / `budget_exhausted` / `failed` |
| `_record_window()` | 写指标 + 假设链 | 假设链在这里组装 |
| `_build_hypothesis()` | 六段式记录 | 判定四档 |
| `_finalize()` | 三种分数 + close | 先算 `final_score`，再补部署分 |
| `_snapshot_runtime()` / `_restore_runtime()` | 状态快照 | 五类状态 |

**最重要的设计：窗口级异常隔离。**

```python
try:
    score, report = self._monitor_and_diagnose(...)
    ...
except Exception as exc:
    self._handle_window_failure(window, runtime, record, exc)
```

任何一步崩了，这个窗口标成失败、分数记 NaN，但**循环继续**，下一个窗口照常处理。整轮跑完 `run_status` 会是 `partial` 而不是直接死掉。这是"无人干预"的前提：一个窗口的坏数据不能毁掉整轮评测。

**另一个细节**：`record.baseline_score` 在窗口开始时存的是"上一窗口部署分"，而不是当前分。因为如果本窗口上线了新模型，`last_deployment_score` 会被更新，那"本窗分数 vs 基线"的对比就永远是 0，漂移证据丢失。

## 4.4 `data\`：数据从哪来

**职责**：把三种数据源统一成 `StreamSource` 协议（`initial_data()` + 迭代出 `DataWindow`）。

### `synthetic.py`：造一份"会变坏"的数据

**实现方法**：8 个特征的二分类数据，分三个阶段：

```text
窗口 0-5    稳定期：X ~ N(0,1)，权重固定
窗口 6-11   渐变期：sensor_00 均值慢慢 +0.9，sensor_01 方差放大，权重逐渐翻转
窗口 12-17  突变期：sensor_00 +1.4、sensor_02 -1.0，权重直接换成另一套
```

再加 8% 的标签噪声（把 8% 的标签随机翻转）。这个噪声很重要：没有它，任何模型都能拿满分，"漂移导致下降"就演不出来。

**可复现性**：每个窗口用 `np.random.default_rng(seed + offset * 7919)` 单独建随机源，而不是全局 `np.random`。这样改窗口数、改窗口大小都不会影响其他窗口的数据——调试时非常关键，否则改一个参数全部结果都变，没法定位。

### `stream.py`：CSV 流，两遍扫描

**实现方法**：先"体检"再"放行"。

```python
header = pd.read_csv(path, nrows=0)          # 只看表头
for chunk in pd.read_csv(path, chunksize=10000):
    validate(chunk)                          # 逐块检查数值性/缺失/无穷
```

第一遍只读表头和分块校验（不把全表读进内存），拿到总行数、特征列、类别数；第二遍才真正迭代窗口。这样 100 万行的 CSV 也只需要常驻一个 chunk 的内存。

**几个硬约束**：

- 窗口至少 10 行（`MIN_WINDOW_SIZE`），太小统计量没意义；
- 特征必须是数值，非数值列直接报错并列出列名——不猜、不自动编码，因为自动编码会悄悄改变语义；
- 尾部不足一个窗口的行被丢弃，并记录 `dropped_tail_rows`；
- 样本 ID 用连续整数，跨 chunk 边界连续（有测试专门验这个）。

### `official.py`：官方数据包适配层（391 行）

**职责**：官方数据包的结构在发布前是未知的，所以不猜目录约定，而是按三级优先级解析。

**实现方法**：

```text
第一级：命令行参数        --target / --initial-file / --stream-file ...
第二级：包内清单          manifest.json / pack.json / manifest.yaml / pack.yaml
第三级：常见命名推断      initial.csv|train.csv|warmup.csv + stream.csv|test.csv|eval.csv
```

三级都定不下来就报错，并且**把找过哪些文件名写进错误信息**：

```text
无法定位stream文件：D:\pack 下没有 stream.csv, test.csv, eval.csv, holdout.csv；
请用命令行参数指定，或在清单中写清楚
```

**预检拦截 7 类问题**（都在启动时，不是跑到一半）：

| 检查 | 拦的是什么后果 |
|---|---|
| 目标列是否存在 | 跑到第 1 个窗口才 KeyError |
| 特征列是否全数值 | 训练时 sklearn 报类型错误 |
| 标签是否有缺失/非有限 | 分数变成 NaN，整轮白跑 |
| 声明的排除列是否存在 | 静默少排除一列，把 ID 当特征训 |
| 初始集行数是否够 `initial_size` | 初始训练集比声明的少 |
| 评测流是否够一个窗口 | 一个窗口都跑不出来 |
| 初始集与流 ID 是否重复 | **守护集与训练集重叠，评估虚高** |

最后一条是这层最值钱的地方。它逐块读 ID 列做集合比对，发现重复就报错并打印示例 ID。

## 4.5 `monitoring\`：判断"世界变了没有"

### `feature_drift.py`：四个统计量 + 一个严重度

**实现方法**：性能优化是这文件的重点。

朴素做法是每个窗口把参考数据重新算一遍分位数——参考集 600 行、8 个特征、18 个窗口，勉强能跑，但数据量一大就废。所以这里做了**参考统计量缓存**：

```python
@dataclass(frozen=True)
class _ReferenceStats:
    sorted_finite_values: np.ndarray   # 排好序的有限值（算 KS 用）
    scale: float                       # 标准差（归一化 Wasserstein 用）
    psi_edges: np.ndarray              # 分桶边界
    psi_ratio: np.ndarray              # 参考集每桶占比
    non_finite_rate: float             # 参考集缺失率
```

KS 统计量也自己实现，用 `np.searchsorted` 算经验 CDF，避免每个特征每个窗口都走一遍 scipy 的完整流程（有测试比对两者结果一致，误差在 1e-12 内）。

**参考集不是一成不变的**：每次部署新模型时调用 `update_reference()`，按 `reference_update_rate`（0.15）混入新数据——保留 85% 旧数据、加入 15% 新数据。这是"尺子慢慢跟着世界走"，否则模型都更新了，尺子还停在半年前，会一直报漂移。

### `performance_drift.py`：两个检测器

`PageHinkley` 只有 15 行，但它是抓"温水煮青蛙"式退化的关键：

```python
self.mean += (value - self.mean) / self.count        # 在线均值
self.cumulative += value - self.mean - self.delta    # 累积偏差
self.minimum = min(self.minimum, self.cumulative)
return (self.cumulative - self.minimum) > self.threshold
```

传入的是 `1 - score`（所以"误差变大"才是上升）。`delta` 是容忍度，过滤微小波动。`threshold` 设为 `max(0.10, drop_threshold * 2)`，跟配置联动，不用单独调一个参数。

**为什么必须攒满 3 个窗口才允许报警**：`enough_history = len(self.scores) == self.scores.maxlen`。前两个窗口就算分很低也不报——因为基线本身还可能不准，太早报警会导致开局就乱更新。

### `diagnosis.py`：把三个信号翻译成一个结论

**实现方法**：一个 if-elif 链，顺序很重要（性能+特征优先判 `mixed`，因为处置方式一样）。

标签漂移用**总变差距离**：

```python
0.5 * sum(|current[label] - reference[label]|)
```

取值 0~1，直观含义是"要挪动多少比例的样本才能让两个分布一样"。比 KL 散度好解释，而且不会因为某个类别缺失就爆炸。

`update_reference_label_distribution` 用指数滑动平均更新参考分布，和特征参考集同步。

## 4.6 `memory\`：回放缓冲区

**职责**：存历史样本，供训练时"复习"。

**实现方法**：三个关键点。

**① 按类分层抽样，不是随机抽。**

```python
quota = max(1, int(round(capacity * count / len(y))))
```

每个类别按它在总体中的比例分配名额。如果随机抽，少数类可能一个都抽不到，候选模型就学不会少数类——而工业缺陷检测里少数类恰恰是最重要的。

**② 按 ID 去重。**

```python
existing = set(self.sample_ids.tolist())
keep = [sid not in existing for sid in incoming_ids]
```

同一个样本重复进缓冲区会人为放大它的权重，等于变相的过采样。

**③ 容量满了就淘汰。**

容量 2400，超了就按分层规则重新选 2400 个。用固定种子的 `rng`，保证同种子跑两次结果一致（可复现性测试会验这个）。

## 4.7 `models\`：模型与版本

### `sklearn_adapter.py`

**职责**：把 sklearn 模型包成统一接口，换模型库时只改这里。

**实现方法**：`task_type` 决定用分类器还是回归器，参数写死在一处：

```python
max_iter=140, learning_rate=0.08, max_leaf_nodes=15, l2_regularization=0.1
```

这组参数是"CPU 上 1~2 秒训完 + 效果够用"的折中。`max_iter=140` 而不是 1000，是因为限时评测里训练时间要计入预算（`budget.max_training_seconds` 累计的是**全部**训练耗时）。

**指标选择**：分类用 `balanced_accuracy_score`，回归用负 RMSE。`metric_name` 属性让摘要里能写清"这个分数是什么指标"，避免看的人误以为是准确率。

### `registry.py`：版本管理

**职责**：存模型、记元数据、支持回滚。

**实现方法**：

```text
models/
├── registry.json     {"current": "v004", "versions": [{version, path, previous, source, score, ...}]}
├── v000.joblib
├── v001.joblib
└── ...
```

**原子写**是核心技巧：

```python
joblib.dump(model, path.with_suffix(".tmp"))
os.replace(temporary, path)     # 原子替换，不会留下半个文件
```

`registry.json` 同样先写 `.tmp` 再替换。这样即使进程被 `kill -9`，也不会出现"注册表说有 v005 但文件是坏的"。

**previous 链**让回滚知道该退到哪：每条记录带 `previous` 字段，`rollback_target()` 顺着链找上一版。

## 4.8 `policy\`：做不做、让不让

### `rule_policy.py`：四道闸门（54 行）

**实现方法**：内部只维护两个状态——`signal_streak`（连续几个窗口有可执行漂移）和 `last_update_window`（上次更新是第几窗）。四个 if 依次返回，每个 `no_update` 都带一句人话理由：

- "当前窗口无可执行漂移"
- "等待漂移连续确认（1/2）"
- "更新冷却期内，还需等待 1 个窗口"
- "漂移已确认，但训练预算不允许"

**这些理由会进 `metrics.csv` 的 `reason` 列和 SwanLab 文本层。**评审想知道"为什么这窗没动"，直接读这句话。

### `hybrid_policy.py`：规则 + LLM

见 3.5。补充实现细节：

- 否决会被**缓存**：`_cached_veto` 存住 LLM 的否决理由，在 `call_cooldown_windows` 内直接复用，返回 `source="llm_cache"`，不重复花 Token；
- LLM 出错时用 `dataclasses.replace` 复制规则决策，只改 `source`/`fallback_reason`/`usage` 几个字段——保证"回退后的决策和规则决策完全一致"，不会因为回退引入行为差异；
- 请求体是 15 个结构化字段（漂移类型、Top 特征、当前分/滚动分/基线分、四类剩余预算、规则理由），**不含原始数据**——LLM 看不到任何一条样本，只看到统计量。这既是隐私边界，也避免它"猜"数据。

## 4.9 `llm\`：模型接入的六个文件（四组职责）

`__init__.py` 只做导出，其余五个文件分工如下。

### `provider.py`：两个数据类 + 一个协议

`LLMDecisionRequest`（15 字段）和 `LLMDecisionResponse`（动作、置信度、理由、模型名、用量、延迟）。协议只有一个 `decide` 方法。

**为什么请求是 frozen dataclass**：防止在传递过程中被意外修改，保证"发给模型的就是记录里写的"。

### `schemas.py`：输出白名单（11 行）

整个 LLM 安全边界的落点。`extra="forbid"` + 枚举限死两个动作 + 置信度 0~1 + 理由长度限制。

### `openai_provider.py`：兼容层（266 行）

**职责**：任何提供 `/chat/completions` 的端点都能用（DeepSeek 官方、vLLM、sglang、mock）。

**实现方法**：处理了五个真实世界的兼容问题。

**① `response_format` 不支持时降级。** 部分 vLLM 版本会返回 400。代码先试带 `response_format={"type":"json_object"}`，失败后判断状态码（400/404/422）或报错信息里有没有 `response_format`，确认是"不支持"才降级重试一次，并记住 `json_mode_disabled = True`，后续不再试。

**② 正文可能是分段列表。** 某些端点的 `message.content` 是 `[{"type":"text","text":"..."}]` 而不是字符串，这里做了拼接。

**③ 推理模型正文为空。** 有些模型只填 `reasoning_content`，`content` 是空字符串。代码会回退去读推理字段。

**④ JSON 可能被包在文字里。** 先 `json.loads`，失败就找第一个 `{` 和最后一个 `}` 再试一次（模型有时候会加"好的，我的判断是："这种前缀）。

**⑤ 错误信息不能泄密。** 所有异常都包装成 `LLMProviderError`，消息里只有端点类型和异常类名：

```python
raise LLMProviderError(f"{self.label} API调用失败（{type(exc).__name__}）")
```

**不包含**请求体、响应体、API Key。这样即使异常被写进日志，也不会泄漏凭据。

返回值里还带 `finish_reason` 和 `total_tokens`，用于诊断"为什么返回空"——是被长度截断了，还是模型没说话。

### `factory.py` / `deepseek_provider.py`

工厂 28 行：按 `provider` 字段分派，`deepseek` 走 `DeepSeekProvider`（其实是 `OpenAICompatibleProvider` 的 13 行别名子类），其余走兼容层。**两条路径共用同一段调用代码**，避免"开发用一套、评测用另一套"导致行为不一致。

`dependency_status()` 顺带探测 `openai` / `swanlab` 装没装、什么版本，供 `env-check` 输出。

## 4.10 `training\`：训候选

`trainer.py` 只有 68 行，逻辑链是三句话：

1. 按 `recent_fraction` 算要抽多少历史样本（`len(recent) * (1-f)/f`）；
2. 抽的时候排除守护集 ID；
3. `champion.new_unfitted()` 建一个空模型，在"回放 + 本窗前 70%"上从头训。

**为什么从头训而不是增量训**：HistGradientBoosting 不支持 `partial_fit`，而且增量训容易让模型对最近的数据过度敏感。从头训虽然慢一点（1 秒内），但每次都是干净的一份模型，行为可预测。

返回值 `TrainingOutcome` 里带 `reference_X`（训练用到的全部数据），部署时用它更新特征参考分布。

## 4.11 `evaluation\`：双考

见 3.3。实现上的一个细节：**历史分可能是 `None`**。

```python
if len(historical_y) > 0:
    ...算两个历史分...
else:
    historical_drop = 0.0    # 没有守护集就不扣分
```

守护集样本数为 0 时（配置成 0），历史考核这一项直接跳过，而不是当成"退化 0"。`champion_historical_score` 字段此时是 `None`，摘要里能看出来"这次没有历史考核"。

## 4.12 `tracking\`：三层留痕

### `local_tracker.py`：本地记录（73 行）

**实现方法**：三个文件，三种写法。

| 文件 | 格式 | 写法 |
|---|---|---|
| `events.jsonl` | 一行一个 JSON | 追加写，`ensure_ascii=False` 保留中文 |
| `metrics.csv` | 表头 + 数据行 | 首行用 `utf-8-sig`（带 BOM，Excel 打开不乱码），之后用 `utf-8` |
| `summary.json` | 缩进 JSON | 覆盖写 |

`_jsonable()` 负责把 `Enum`、`Path`、`np.int64`、嵌套 dict/list 递归转成可序列化类型。这个函数看着琐碎，但没有它，`np.float64` 会让 `json.dumps` 直接抛错——而 pandas/numpy 里到处都是这种类型。

### `swanlab_tracker.py`：云端镜像（468 行）

**实现方法**：五个模块。

**① 模式解析。** `_resolve_mode` 判断：如果不是 online 就直接用；如果是 online 但没 `SWANLAB_API_KEY` 也没有 `~/.swanlab/.netrc`，就降级成 offline 并返回一句原因。

为什么必须这么做？实测过：SwanLab 在没有凭据时会打印"请输入 API Key"并等标准输入。在 ConPTY 环境下 `isatty()` 返回真，所以它以为有终端，结果**整个无人值守的运行就挂在那里**。这是"评测机不能挂"的直接教训。

**② 数值化上报。** `log_metrics` 只发数值：数值直接转 float，布尔转 0/1，字符串状态查 `_CODEBOOK` 转码，查不到的丢弃。一列都映射不出来时**不发空包**，避免在看板上造一列空数据。

**③ 文本层。** `_render_hypothesis` 把六段结构渲染成 Markdown，带 emoji 判定标记（✅/❌/➖/⏭️）。这样在 SwanLab 的文本面板里直接可读，不用点开 JSON。

**④ 产物上传。** `close()` 时按 `summary.json` → `metrics.csv` → `events.jsonl` → `models/registry.json` 顺序上传，每个文件先查大小（超过 `artifact_max_mb` 就跳过并记一条失败），再 `run.save(policy="now")` 立即上传。

**⑤ 能力探测。** `_supports_text` / `_supports_save` 用 `callable(getattr(...))` 探测。老版本 SwanLab 没有 `log_text`，探测后自动降级，不会因为接口差异炸掉整轮运行。

### `CompositeTracker`（同文件后半段）

主记录 + 若干镜像。三条规则：

1. 每个写操作**先写主记录，再通知镜像**；
2. 镜像失败只记事件，不抛异常；
3. **连续失败 5 次**才停用该镜像，偶发抖动不踢。

`close()` 的顺序是"先本地、再镜像"——保证看板掉线时本地证据一定完整。

# 第 5 章 四个产物文件怎么读

## 5.1 `events.jsonl`：18 类事件（标准运行约 140 条）

每行一个 JSON：`{timestamp, run_id, event_type, payload}`。事件是**因果链**，顺序就是发生顺序。

| 事件 | 何时写 | 关键字段 | 能查出什么 |
|---|---|---|---|
| `state_transition` | 每次状态跳转 | from / to / window | 闭环是否真的走完、卡在哪 |
| `initial_model_ready` | 初始模型训练完 | version / score / 样本数 / 耗时 | 冷启动质量与成本 |
| `drift_diagnosis` | 每窗诊断后 | report（完整漂移详情） | 每窗的四类指标与结论 |
| `update_decision` | 决策后 | action / reason / source / budget | 为什么动/不动、谁决定的 |
| `llm_decision` | LLM 实际调用后 | model / confidence / usage / latency | Token 花在哪、延迟多少 |
| `llm_fallback` | 回退时 | reason | 降级原因分布 |
| `candidate_evaluated` | 双考完成 | evaluation（6 个分数） | 候选为什么被拒 |
| `model_deployed` | 上线 | version / evaluation | 哪个版本、什么成绩上线 |
| `model_rolled_back` | 回滚 | from/to version / 回滚后分数 | 退化有多严重 |
| `window_failure` | 窗口失败 | error_type / error / fallback_version | 失败原因归类 |
| `final_deployment_summary` | 收尾 | 三种分数对照 | 最终模型的真实成绩 |
| `final_deployment_score_missing` | 收尾（无部署评估） | 原因 | 为什么这个字段是 null |
| `swanlab_attached` / `swanlab_disabled` | 记录器初始化 | mode / url / reason | 记录通道状态 |
| `tracker_mirror_failure` | 镜像写失败 | mirror / method / consecutive | 云端抖动情况 |
| `tracker_mirror_disabled` | 连续 5 次失败 | consecutive_failures | 镜像被停用 |
| `hypothesis_recorded` | 每窗结束 | 六段式结构 | 判断链全文 |
| `run_completed` | 收尾 | 完整 summary | 与 summary.json 一致 |

## 5.2 `metrics.csv`：一窗一行，按列分组

| 组 | 列 | 用途 |
|---|---|---|
| 定位 | `window` `phase` `state` `model_version` `scored_model_version` `deployed_model_version` | 这是第几窗、什么阶段、模型是哪版 |
| 效果 | `score` `candidate_improvement` | 分数与候选提升 |
| 漂移 | `drift_kind` `feature_drift_score` `performance_drop` `label_shift` | 四类漂移证据 |
| 动作 | `action` `status` `reason` | 做了什么、结果、为什么 |
| LLM | `llm_attempted` `llm_called` `decision_source` `llm_model` `llm_confidence` `llm_*_tokens` `llm_latency_seconds` `llm_fallback_reason` | 谁决策、花了多少 |
| 预算 | `updates_used` `training_seconds_used` `labels_used` `tokens_used` `budget_violations` | 四类资源的累计曲线 |

**这张表的正确用法是画折线图**：横轴 `window`，纵轴 `score`，按 `deployed_model_version` 上色——一眼能看出"哪次上线真的有用"。

## 5.4 `models\registry.json`：版本链

```json
{
  "current": "v004",
  "versions": [
    {"version": "v000", "path": "v000.joblib", "previous": null,
     "source": "initial", "score": 0.734093, "training_seconds": 2.068564},
    {"version": "v001", "path": "v001.joblib", "previous": "v000",
     "source": "window_7", "score": 0.649832, "training_seconds": 1.308536},
    {"version": "v002", "path": "v002.joblib", "previous": "v001",
     "source": "window_11", "score": 0.711429, "training_seconds": 1.316958},
    {"version": "v003", "path": "v003.joblib", "previous": "v002",
     "source": "window_13", "score": 0.7375, "training_seconds": 1.296079},
    {"version": "v004", "path": "v004.joblib", "previous": "v003",
     "source": "window_17", "score": 0.660055, "training_seconds": 1.232034}
  ]
}
```

**注意一个容易误读的地方**：v000 的 0.734 是**初始验证集**上的分数，v001 之后记的都是**各自窗口 holdout** 上的分数。两者不是同一份数据，不能直接比大小。v001 在窗口 7 上线时 holdout 只有 0.649832，但它是"通过了比冠军更高"这道门槛的——门槛比的是同一份 holdout 上冠军和候选的差，不是和 0.734 比。

这也正是摘要要单独给出 `final_deployed_score` 的原因：模型版本之间分数不可横比，只有"候选 vs 冠军在同一份数据上"的差才有意义。

`previous` 字段就是回滚路径。想知道"第 7 窗训了什么"，看 `source`；想看"它当时考了多少分"，看 `score`。

|---|---|---|
| `initial_samples` | 冷启动样本数 | 初始模型更稳，但标签预算消耗更快 |
| `window_size` | 每窗样本数 | 统计量更稳，但响应变慢、holdout 训练样本变少 |
| `n_windows` | 窗口总数 | 跑得更久，接触更多漂移阶段 |
| `n_features` | 特征数 | 漂移信号更多元，计算量线性增加 |
| `gradual_drift_start` | 渐变从第几窗开始 | 越大越晚遇到漂移 |
| `abrupt_drift_start` | 突变从第几窗开始 | 必须 < `n_windows` |
| `label_noise` | 标签噪声比例 | 越大越难学，必须 < 0.5 |

**约束**：`gradual_drift_start < abrupt_drift_start < n_windows`，启动时校验。

## 6.3 `monitoring`

| 字段 | 含义 | 建议值 | 调小会怎样 | 调大会怎样 |
|---|---|---|---|---|
| `psi_threshold` | PSI 报警线 | 0.18 | 误报变多 | 漏报变多 |
| `ks_threshold` | KS 报警线 | 0.18 | 同上 | 同上 |
| `performance_drop_threshold` | 掉多少分算性能漂移 | 0.06 | 一抖动就报 | 真掉分了也不报 |
| `label_shift_threshold` | 标签分布变化线 | 0.12 | 类别比例微调就报 | 严重失衡才报 |
| `consecutive_windows` | 连续几窗确认才允许更新 | 1（tuned）/ 2（default） | 反应快但易误触发 | 反应稳但慢半拍 |
| `reference_update_rate` | 参考集每次混入新数据的比例 | 0.15 | 尺子更新慢，长期报漂移 | 尺子跟太快，漂移被"吸收"掉 |
| `min_valid_feature_values` | 最少有效值个数 | 5 | 更容易熔断 | 垃圾数据也能算 |
| `non_finite_rate_threshold` | 缺失率变化报警线 | 0.10 | 缺一点就报 | 缺一半才报 |

**最容易踩的坑**：`reference_update_rate` 设成 1.0 会让参考集每次完全变成新数据，漂移永远检测不到（尺子跟着数据一起变，量出来永远是 0）。

## 6.4 `policy`

| 字段 | 含义 | 注意 |
|---|---|---|
| `cooldown_windows` | 更新后几窗内不许再更新 | 0 表示不冷却，容易连环训练烧预算 |
| `rollback_patience` | 连续几窗退化才回滚 | 1 表示一窗就回滚，容易被抖动带走 |
| `rollback_drop` | 比部署分低多少算退化 | 太小会频繁回滚，太大会一直不救 |

## 6.5 `training`

| 字段 | 含义 | 计算方式 |
|---|---|---|
| `replay_capacity` | 回放池最大容量 | 超了按类分层重选 |
| `recent_fraction` | 新数据占比 | 回放条数 = `len(recent) × (1-f)/f` |
| `max_replay_samples` | 单次回放上限 | 防止一窗拿太多历史，训练变慢 |
| `holdout_fraction` | 留作考试的比例 | 必须 0.05~0.5，默认 0.30 |

**`recent_fraction` 的直觉**：0.65 表示"新 65%、旧 35%"。调到 0.9 容易忘旧知识（守护集会掉），调到 0.3 学不到新规律（holdout 提升不够）。

## 6.6 `validation`

| 字段 | 含义 | 建议 |
|---|---|---|
| `min_improvement` | holdout 至少要提升多少 | 0.008；设 0.03 以上会导致几乎不更新 |
| `max_historical_drop` | 守护集最多允许退多少 | **0.10**；设 0.06 实测导致零更新 |
| `guard_samples` | 守护集样本数 | 500~800；太小评估噪声大 |

## 6.7 `budget`

| 字段 | 含义 | 实测值 |
|---|---|---|
| `max_updates` | 最多训练几次 | tuned 6 / official 8 / static **0** |
| `max_training_seconds` | 累计训练秒数 | 120 / 240 |
| `max_labels` | 最多见多少个不同标签 | 5000 / 20000 |
| `max_tokens` | LLM Token 上限 | 0（不接 LLM）/ 8000 |

**`max_tokens: 0` 是一个重要设计**：默认配置下 LLM 完全不可用（`HybridPolicy` 发现剩余 Token 不够就不会调用），所以离线配置的 Token 成本恒为 0，可以放心跑。

## 6.8 `tracking`

| 字段 | 含义 | 默认 |
|---|---|---|
| `run_root` | 产物根目录 | `runs`（相对路径，容器里是 `/app/runs`） |
| `enable_swanlab` | 是否开镜像 | false（容器里由 `IE_SWANLAB=1` 打开） |
| `swanlab_mode` | online / local / offline / disabled | online（无凭证自动降级 offline） |
| `swanlab_project` | 看板项目名 | `industrial-evolution` |
| `swanlab_log_dir` | 落盘目录 | `<run_root>/.swanlab` |
| `swanlab_tags` | 标签 | `["industrial-evolution"]` |
| `swanlab_upload_artifacts` | 是否上传产物 | true |
| `swanlab_artifact_max_mb` | 单文件上限 | 64 |

## 6.9 `llm`

| 字段 | 含义 | 备注 |
|---|---|---|
| `enabled` | 总开关 | false 时走纯规则，Token 恒 0 |
| `provider` | `deepseek` / `openai_compatible` | 前者锁官方域名 |

3. **`tuned.yaml` 的参数是按合成流调的。** 拿到官方数据后必须重标（第 9 章列了具体要改哪几个）。

## XJTU-SY 轴承全寿命数据接入（新增）

### 数据清单核验

本机 `D:\桌面\XJTU-SY轴承数据集\Data\XJTU-SY_Bearing_Datasets` 中实际统计到 9,216 个 `.csv` 文件，另有 1 个 PDF；CSV 数量与数据说明列出的 15 个轴承数量之和完全一致。逐 bearing 核验结果：35Hz12kN 为 616 个，37.5Hz11kN 为 1,566 个，40Hz10kN 为 7,034 个；15 个目录内文件序号均从 1 连续至各自末尾，无缺号、非数字命名或额外序号。此前 Glob 工具返回 9,225 个匹配项，但目前独立递归枚举未复现这 9 个差额，原因尚未查明；因此不把它们解释成额外 CSV，也不宣称 Glob 差额已被完全追溯。

### 怎么接入与运行

`data/real_datasets.py` 的 `XjtuBearingStream` 强制指定一个工况和一个轴承，只用文件名数字排序。每份 CSV 读入后聚合为一行 12 维特征：水平与垂直通道各取均值、标准差、RMS、峰峰值、偏度、超额峰度。缺列、空文件、非有限值、非数字文件名、缺失序号和目录不存在都会明确报错。每个样本 ID 包含工况、轴承和文件序号，避免不同轴承之间账本 ID 重叠。尾部不够完整窗口的记录会被丢弃并留在 `dropped_tail_rows`。

```powershell
.\.venv\Scripts\python.exe -m industrial_evolution.cli run-xjtu `
  --data-dir "D:\桌面\XJTU-SY轴承数据集\Data" `
  --condition 40Hz10kN --bearing Bearing3_1 --config configs\xjtu.yaml
```

RUL = 已知全寿命序列最后文件序号 − 当前文件序号，单位分钟，且不做 130 截断。这个标签依赖已完整观测到的失效终点，仅可用于全寿命离线实验；它**没有解决在线标签延迟**，不能宣称现场实时数据到达时答案已知。单轴承时间顺序保留；不同轴承是相互独立试验，禁止拼接成一条伪连续流。`configs/xjtu.yaml` 的阈值是 RMSE 量级的保守起点，必须等官方评分规则明确后用静态基线校准。

工程 smoke test 使用 `40Hz10kN/Bearing3_1` 的完整 2,538 个分钟样本：48 个窗口全部完成、0 失败、Token 0；但最终负 RMSE 从初始 `-32.440995` 降至 `-2451.863314`，8 个候选均被拒绝，没有模型上线。该结果明确说明**数据接入与闭环可运行，但预测效果很差，不能宣称优于基线**；应优先检查特征与 RUL 关系、时间跨度、模型适配及基线后再调参。这个实验使用全寿命标签，不符合在线标签可见性证明。

工程接入成功不等于模型效果达标。自动化测试与真实轴承 smoke test 只验证读取、聚合、标签、切窗和闭环可运行，不证明优于静态模型或达到比赛指标。

# 第 9 章 已知限制（按优先级）

| 级别 | 问题 | 现象 | 影响 | 建议做法 |
|---|---|---|---|---|
| **P0** | 标签延迟未建模 | 窗口数据一到就假设标签可用并计费 | 真实场景标签可能滞后 N 天，当前模型会"提前用未来标签" | 给 `StreamSource` 加"窗口未标注"状态，标签到达后再触发评估；预算账本改为"标签到达时计费" |
| **P1** | XJTU-SY 离线 RUL 标签假设 | RUL 由完整寿命的最后文件序号推导 | 在线时未知终点，不能据此声称已解决标签延迟 | 已新增单轴承离线适配器；需另行实现标签到达延迟模型 |
| **P0** | 官方评测脚本未直连 | 只输出自己的 `summary.json` | 评测方要手工对指标，容易对错 | 拿到官方脚本后写一个适配器，把 `final_deployed_score` 映射到官方指标名 |
| **P1** | 决策链只有 1 次"同意/否决" | `hybrid_policy` 只在规则已决定训练时参与 | 赛题要求"≥3 次决策"，当前不满足 | 让 LLM 能读最近 N 窗的历史实验记录，形成"提出假设→验证→修正"的多轮链；需扩展协议传历史摘要 |
| **P2** | 实际资源超限只能事后确认 | API 返回实际 Token 或训练完成后测得耗时超过剩余额度 | 已发生的调用/训练成本无法撤销，当前窗口按 `budget_exhausted` 熔断，不评估/上线候选 | 保留硬熔断与违规留痕；若需降低发生概率，再增加耗时估算或按官方成本规则校准预留额度 |
| **P2** | 无 `.git` / `LICENSE` | 项目目录没有版本库和许可证 | 交付规范性扣分 | `git init` + 加 MIT/Apache-2.0（按赛题要求） |
| **P2** | `dist` 的 tar 未压缩 | 540 MB | 传输慢 | `gzip` 后可到约 200 MB，或改用 `docker save \| zstd` |
| **P2** | Windows 上 SwanLab 离线产物的 symlink 是断链 | 资源管理器里看到箭头打不开 | 不影响上传成功（云端是实体文件），但本地看会困惑 | 文档里已说明；或在 Windows 上改为复制而不是链接 |
| **P2** | 特征只支持数值 | 类别型特征要人工编码 | 接入成本 | 加一层"声明式编码"配置（one-hot / target encoding），但必须记录编码表以防泄漏 |

# 附录 A 术语表

| 术语 | 大白话 |
|---|---|
| **数据漂移** | 模型见过的世界变了，导致它的判断开始不准 |
| **协变量漂移** | 输入数据的分布变了，但"输入→输出"的规律还没变 |
| **概念漂移** | 输入没怎么变，但规律本身变了（同样的参数，结论不一样了） |
| **标签漂移** | 各类样本的比例变了（比如缺陷率从 3% 涨到 15%） |
| **PSI** | 把数据分成 10 个桶，比较每桶人数占比的变化；0.1 小幅、0.25 显著 |
| **KS** | 两条累积分布曲线之间最远的距离 |
| **Wasserstein 距离** | 把一堆土搬成另一堆形状要费多少力（推土机距离） |
| **Page-Hinkley** | 专门抓"缓慢持续下降"的累积和检验 |
| **holdout** | 本窗口留出来不参与训练的那部分数据，用来当堂小测 |
| **守护集** | 从初始验证集切出来的固定样本，永不参与训练，用来当"高考真题" |
| **回放（replay）** | 训练新模型时混入历史样本，防止忘掉旧知识 |
| **平衡准确率** | 每个类别各算召回率再平均，避免被多数类带偏 |
| **冠军/挑战者** | 当前线上模型 vs 新训出来的候选 |
| **原子写** | 先写临时文件再整体替换，保证不会读到半个坏文件 |
